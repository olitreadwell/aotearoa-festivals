# Decision Framework

Four questions, in order. Stop at the first one that answers yes.

## 1. Is this a simple, static layout or spacing property?

If yes, use **Tailwind**.

```tsx
<div className="flex flex-col gap-4 px-6 py-12">
```

No states involved. No variants. Position on the page.

## 2. Does this style define a component variant or named state?

If yes, create a **SCSS class**.

A "primary" button or a "secondary" button is a *named* thing. Name it.

```scss
.numeral-button-primary { background: var(--color-fg); }
.numeral-button-secondary { background: transparent; box-shadow: inset 0 0 0 1px var(--color-border); }
```

## 3. Does the style involve complex pseudo-states that change multiple properties?

If yes, define in **SCSS**.

Hover on a card that lifts, dims its siblings, and reveals an icon — that's three coordinated property changes. Tailwind can do it, but you'll regret reading it in six months.

```scss
.numeral-card {
  transition: transform var(--duration-200) var(--ease-out);

  @include hover {
    &:hover {
      transform: translateY(-2px);

      .numeral-card-icon { opacity: 1; }
      & + .numeral-card { opacity: 0.6; }
    }
  }
}
```

## 4. Is your className becoming long and unreadable?

If yes, abstract into **SCSS**.

This is the catch-all. If the answer to 1, 2, 3 was no but your `className` has more than ~6 utilities, you're making the JSX harder to scan. Pull the visual concern into SCSS and reference it once.

---

**Bias toward Tailwind by default.** It's easier to delete, easier to grep for, and doesn't carry a name. Escalate to SCSS when complexity or readability demands it.
